## 2. 🔴 먼저 선을 긋자 — 여기만 지키면 나머지는 다 해도 된다

준희가 말한 **"AI 티가 안 났으면 좋겠다"** 는 사실 **두 가지가 섞여 있다.** 나눠서 보면 답이 나온다.

| | 뜻 | 평가 |
|---|---|---|
| **㉮ 문체가 자연스러울 것** | 번역투·설명조·"~네요!" 남발이 없을 것 | 🟢 **완전히 정당하고, 이게 진짜 과제다.** 여기에 힘을 쏟자 |
| **㉯ 운영자가 쓴 글임을 숨길 것** | 일반 학생인 척 | 🔴 **리스크가 있다.** 아래 참조 |

### ㉯가 왜 위험한가 (사실 관계)
- **일본 景品表示法 — 스텔스 마케팅 규제** (2023년 10월 1일 시행, 消費者庁 고시).
  **사업자가** 자기가 공급하는 상품·서비스에 대해 하는 표시인데 **일반 소비자가 사업자의 표시라고
  판별하기 어려운** 것을 부당표시로 금지한다. **고의·과실을 묻지 않고** 措置命令(행정처분) 대상이며,
  2024년 6월에 첫 명령이 나왔다.
  - ⚠️ 정확히 하면: 「스루가다이 흡연실 어디예요?」 같은 **잡담 글**은 "자사 서비스의 거래에 관한 표시"가
    아니라서 이 조문에 바로 걸린다고 단정할 수 없다. 나는 변호사가 아니고 이건 확정적 해석이 아니다.
    반면 **"이 앱 좋네요" 류의 자화자찬 글·가짜 리뷰는 명백히 대상**이다.
- **스토어 정책**: Apple·Google 모두 **가짜 계정·조작된 참여(fake engagement)** 를 금지한다.
  커뮤니티 앱에서 운영자가 유저인 척 대량 투고하는 것은 신고 시 제재 사유가 될 수 있다.
- **가장 현실적인 리스크는 신뢰다.** 유저 몇 명만 눈치채면 끝이다. 학생 커뮤니티는 소문이 하루면 돈다.
  "여기 글 다 운영자가 쓴 거래"는 **되돌릴 수 없는 평판 손상**이다.

### 🟢 그래서 이렇게 하면 된다 — **㉮는 100% 가져가고, ㉯만 포기한다**

핵심 재구성:
> **"운영 계정이 쓴 글"이라고 표시해도, 글이 재미있으면 사람은 온다.**
> 오히려 **공식 계정이 도발적인 질문을 던지면 유저는 댓글로 답한다.** 그게 커뮤니티가 사는 방식이다.
> 숨겨서 얻는 이득은 작고 잃을 것은 크다. **표시하고, 대신 글을 훨씬 재밌게 쓰자.**

실제 설계 (§3)에서 이걸 구체화한다.

### 🔴 절대 금지 (이건 선택지가 아니다)
1. **가짜 강의평 생성** — 존재하지 않는 수강 경험을 지어내는 것. 景表法 + 교원 명예훼손 리스크
2. **자사 앱 홍보를 유저인 척** 하는 글 — ステマ 규제 정면 대상
3. **가짜 계정 대량 생성** — 스토어 정책 위반
4. **타 앱 데이터 무단 복제** (§8 참조)

## 3. 운영 계정 설계 — 🔴 준희 결정

### 공통 전제
- 글 자체는 **익명 표시**(현행 유지). 다만 **운영 글에는 구분 표식**을 붙인다.
- 표식은 **작게, 그러나 거짓말이 아니게**. 숨기지 않되 분위기를 깨지도 않게.

### 안 ①: **「森の管理人」(숲의 관리인)** — 🟢 권장
- 표시: 작성자가 `森の管理人` + 작은 배지. 탭하면 "운영팀이 올린 화제입니다" 한 줄
- 성격: **화제를 던지는 역할**. 질문형·토론형 글 위주. 답은 유저가 단다
- 👍 브랜드 세계관과 맞고(大学の森), 숨기지 않으며, 질문형이라 참여를 부른다
- 👍 나중에 공지·이벤트도 이 계정으로 → 자산이 쌓인다

### 안 ②: **「今日の話題」 데일리 토픽 섹션**
- 글이 아니라 **섹션**으로 분리. 게시판 상단에 매일 1개 고정
- 👍 가장 깔끔하고 오해 여지가 없다 / 👎 일반 글 흐름에 안 섞여서 체감 활성도 기여가 적다

### 안 ③: 비표시 (일반 유저처럼)
- 👎 §2의 리스크 전부. **권장하지 않는다.**

> 🟢 **Claude 권고: ①을 기본으로, ②를 함께.**
> 평소 글은 「森の管理人」이 올리고, 그중 반응이 좋은 걸 「今日の話題」로 고정 노출.
> 그리고 **㉮(문체)에 전력을 쏟는다** — 이게 진짜 승부처다.

## 4. "AI 티"를 없애는 방법 — 문체 규칙 (㉮)

AI 글이 들키는 건 출처 표시 때문이 아니라 **문장 습관** 때문이다. 다음을 규칙으로 고정한다.

### 하지 말 것
- `〜ですね！` `〜しましょう！` 남발, 느낌표 과다
- 균형 잡힌 결론 (「でも人それぞれですよね」) — **학생은 단정한다**
- 3개씩 나열하는 습관 (「安い・近い・美味しい」)
- 제목이 완결된 문장 — **학생 글 제목은 말을 흐린다** (「スルガ台の喫煙所どこ…」)
- 이모지 과다, 머리말·맺음말
- 설명조 ("~について解説します")

### 할 것
- **짧게 끊기.** 1~3문장이 대부분. 길어도 5줄
- **말 흐리기**: `〜かな` `〜って話` `〜らしい` `誰か教えて`
- **구체 고유명사**: 「駿河台」「リバティタワー」「和泉の食堂」「ゼミ」「1限」 — 구체성이 진짜처럼 만든다
- **감정이 먼저, 정보는 나중**: 「1限きつすぎる」 → 그다음 설명
- **질문으로 끝내기**: 댓글이 달려야 글이 산다
- 오탈자·구어체 허용 (`てか` `まじで` `草`)

> 📌 이 규칙은 세션 S5에서 **생성 프롬프트에 그대로 박는다.** 글 품질의 90%가 여기서 결정된다.

## 5. 소재 파이프라인 — "계속 찾고 관리해서 지속 업로드"

준희가 말한 **"내가 아이디어를 주는 데는 한계가 있다"** 가 핵심이다. 그래서 **소재가 자동으로 흘러들어오는 관**을 만든다.

```
[A. 소스 감시]  →  [B. 소재 큐]  →  [C. 각색]  →  [D. 검수]  →  [E. 게시]
  주 1회 수집        JSON 파일       문체 규칙      준희 승인     Firestore
```

### A. 소스 (주 1회, Claude가 WebSearch로 수집)
| 소스 | 뭘 보나 | 쓰임 |
|---|---|---|
| **X(구 트위터)** 대학 태그 | `#春から明治` `#大学生あるある` 등 화제 | 🟢 일본 20대 관심사 1순위 |
| **일본 뉴스 조회수 상위 제목** | Yahoo!ニュース 국내 랭킹 | 제목 짓는 법 학습 + 시사 네타 |
| **나무위키·위키** 대학 항목 | 알아두면 쓸모있는 잡지식 | 「知らなかった」류 글 |
| **디시 해외대학 갤러리** | 일본 유학 관련 화제 | 🟢 한국인 유학생 관점 |
| **Reddit** r/japanlife, r/japanuniversity | 외국인 학생 고민 | 유학생 공감대 |
| **에브리타임 화제글 유형** | 구조만 참고 (문장 복사 금지) | 글 유형 카탈로그 |
| **메이지 공식** 학사일정·이벤트 | 시험기간·축제·휴강 | 🟢 시의성 = 반응 최고 |

> ⚠️ **참고하는 것과 복사하는 것은 다르다.** 남의 글을 그대로 옮기면 저작권 문제다.
> **유형·주제만 가져오고 문장은 새로 쓴다.** (예: "학식 티어표가 반응이 좋더라" → 우리 학식으로 새로 작성)

### B. 소재 큐 — 저장소에 파일로
```
docs/content/
  neta.md          ← 🟢 준희가 생각날 때 한 줄씩 적는 곳 (대학생활에서 느낀 점 등)
  queue.json       ← 각색 전 소재 (수집 결과)
  drafts/2026-11.json  ← 각색 완료 글 (게시 대기)
  posted.json      ← 게시 완료 기록 (중복 방지)
```
**준희가 할 일은 `neta.md`에 생각날 때 한 줄 적는 것뿐.** 나머지는 Claude가 돌린다.

### C·D. 각색 → 검수
- Claude가 `queue.json` + `neta.md` → §4 문체 규칙으로 각색 → `drafts/`에 JSON
- **준희가 drafts를 훑고 X 표시만** (전부 읽을 필요 없음, 이상한 것만 걷어내기)

### E. 게시
- 준희 PC에서 적재 스크립트 실행 (서비스 계정 키가 준희 PC에만 있음)
- `scripts/post-content.mjs` — drafts JSON → Firestore, **시간을 흩뿌려서** 적재
  (한 번에 50개가 같은 시각에 뜨면 바로 들킨다. **하루 5개, 시간대 랜덤**이 자연스럽다)

### 🔴 준희가 제시한 소재 중 **바꿔야 할 것 하나**
> 「〇〇の授業、美人多くない？」
- **그대로는 권하지 않는다.** 이유 셋:
  1. 외모 품평이 특정 수업·특정인 지목으로 흐르면 **신고·명예훼손** 대상이 된다
  2. **여학생이 바로 이탈한다.** 커뮤니티 성비가 무너지면 회복이 안 된다 (타 커뮤니티에서 반복 검증된 패턴)
  3. 스토어 심사에서 신고가 누적되면 **연령등급·앱 존속** 문제로 번진다
- 🟢 **같은 재미를 주는 대체 소재**:
  「この授業、なぜか人気で抽選落ちた」 / 「教室の雰囲気がいい授業」 /
  「授業で隣の席の人と friendly になった話」 / 「キャンパスで一番おしゃれな学部はどこ」

## 7. 금지 소재 (규칙으로 고정)

## 8. 강의평 시딩 — 🔴 "다른 앱에서 가져오기"는 못 한다

### 사실 관계부터
준희가 든 쿠팡이츠-구글 리뷰 사례는 **Google Places API를 라이선스 받아 쓴 것**이지
남의 데이터를 긁어온 게 아니다. 그래서 그 방식을 그대로는 못 따라간다.
- 타 앱(Penmark 등)의 강의평을 긁어오는 것 = **이용약관 위반 + 데이터베이스 권리 + 저작권** 문제.
  소송까지 안 가도 **스토어 신고 한 번이면 앱이 내려간다.** 이건 위험 대비 이득이 너무 나쁘다.
- 🔴 **가짜 강의평 생성도 안 된다** — 존재하지 않는 수강 경험을 지어내는 것은 §2의 1번 금지 항목.
  강의평은 **다른 학생의 이수 결정에 직접 영향**을 주므로, 커뮤니티 잡담과 질이 다르다.

### 조사 결과 (2026-10-28)
明治大学의 「授業改善アンケート」는 공개돼 있지만 **학부·클래스 규모 단위 집계**(예: 50~100명 수업의
사전학습 시간 평균)라서 **과목별 평가가 아니다.** 「꿀강인가」에 답을 못 준다. → **공식 데이터로는 시딩 불가.**

### 🟢 그래서 이렇게 간다 — 3단 전략

**① 객관 정보부터 채운다 (지금 당장 가능, 법적으로 완전히 안전)**
- 이미 가진 시라버스 20,022건에는 **成績評価方法·到達目標·授業形態** 같은 필드가 들어 있다
- 이걸 **구조화해서 강의 상세에 "시라버스 정보" 섹션**으로 표시
  → 「テスト100%」「レポート中心」「出席点あり」 같은 건 **평가가 아니라 사실**이다. 공식 정보라 안전하고,
  학생이 가장 알고 싶어 하는 것의 **절반은 여기서 해결된다**
- 👉 **리뷰 0건이어도 강의 상세가 비어 보이지 않는다.** 이게 콜드스타트의 핵심
- ⚠️ 크롤 시 현재 저장 필드 확인 필요 → 세션 S7 첫 작업

**② 리뷰를 쓰게 만든다 (에타 방식)**
- **"리뷰 1개 쓰면 전체 열람"** — 에타가 검증한 구조. 기여 없이 열람하면 아무도 안 쓴다
- 시간표에 등록한 강의 → 학기 말에 **"이 수업 어땠어요?" 1탭 평가** (별점 + 태그만, 텍스트는 선택)
  → 이미 `REVIEW_TAGS` 8개가 구현돼 있다. **마찰을 최소화하는 UI만 붙이면 된다**

**③ 운영진이 직접 쓴다 (정직하게)**
- 준희·태희가 **실제로 들은 수업**의 리뷰를 쓴다. 이건 진짜 리뷰다
- 상학부 4년이면 수십 과목 — **그 자체가 초기 시드**다
- 베타 테스터 12명에게도 부탁 (안드로이드 테스터 모집과 겸함)

## 9. 기술 구현 (세션 S5)

### 제약
🔴 **Firebase 서비스 계정 키가 준희 PC에만 있다.** 그래서 **완전 자동 게시는 지금 구조로는 불가능**하다.
선택지:
| 방식 | 필요 | 평 |
|---|---|---|
| **A. 로컬 스크립트 + 준희 실행** | 없음 | 🟢 지금 바로 가능. 주 1회 5분 |
| B. Cloud Functions 스케줄 | **Blaze 전환** | 완전 자동. 비용 발생. 1.2 이후 |
| C. Claude 정기 세션 | 키 공유 필요 | 🔴 보안상 권장 안 함 |

> 🟢 **A로 시작한다.** Claude가 drafts를 커밋 → 준희가 `git pull` 후 스크립트 1줄 실행.
> 유저가 늘어서 Blaze로 갈 때 B로 이전한다.

### 만들 것
```
scripts/content/
  collect.mjs      소스 감시 결과 → queue.json (Claude가 WebSearch로 채우므로 사실상 수동)
  post.mjs         drafts/*.json → Firestore. 시간 분산·중복 체크·금칙어 재검사
docs/content/
  neta.md  queue.json  drafts/  posted.json
src/types/post.ts 에 필드 1개 추가 검토:
  official?: boolean   ← 운영 글 표식 (🔴 타입 변경 = 태희 창구, firestore.rules 동시 수정)
```

### 운영 리듬 (주 1회 30분)
| 요일 | 누가 | 무엇 |
|---|---|---|
| 월 | Claude | 소스 감시 → queue 갱신 → 7~10개 각색 → drafts 커밋 |
| 화 | 준희 | drafts 훑고 X 표시 → `post.mjs` 실행 |
| 수~일 | 자동 | 스크립트가 예약한 시각에 하루 1~2개씩 게시 |
