## 1. 현재 실제로 어떻게 돼 있나 (코드 기준, 추측 아님)

### 1-1. 공간은 이미 3층이다
| 층 | Firestore 경로 | 앱에서 | 범위 |
|---|---|---|---|
| **학교 게시판** | `schools/{schoolDomain}/boards/{boardId}/posts` | 게시판 탭 — 自由/留学生/質問/教科書ゆずり/サークル + 유저생성 | 학교별 분리 |
| **학부 게시판** | 위와 동일 (`category: "department"`) | 게시판 탭의 「学部」 섹션 | 학교 안에서 학부별 |
| **유학생 라운지** | `lounges/{loungeId}/posts` | 게시판 탭 상단 배너 → 별도 화면 | **전국 공통** |

즉 **구조는 에타의 「캠퍼스 / 연합」과 이미 같다.** 문제는 구조가 아니라 **권한**이다.

### 1-2. 🔴 권한에 구멍이 셋 있다

**① 학교 게시판에 소속 검증이 전혀 없다**
```
match /schools/{schoolDomain} {
  match /boards/{boardId}/posts/{postId} {
    allow read: if isSignedIn();              // ← schoolDomain 검증 없음
    allow create: if canWriteContent() && isAuthor();
```
`firestore.rules:244-246`. **로그인만 했으면 아무나 아무 학교 게시판을 읽고 쓸 수 있다.**
지금 분리돼 보이는 건 **앱 UI가 자기 학교 경로만 조회하기 때문**이지, 서버가 막는 게 아니다.
Firebase 설정(API 키)은 앱에 들어 있으므로 마음먹으면 타교 게시판에 글을 쓸 수 있다.
→ **유출 사고는 아니다**(개인정보가 새는 게 아님). 하지만 "우리 학교만 보는 공간"이라는 약속이 지금은 **UI 약속일 뿐**이다.

**② 익명 게스트도 글을 쓸 수 있다**
```
function canWriteContent() { return isSignedIn(); }   // firestore.rules:36-39
```
주석에 「初期: 匿名ゲストも書き込み可 / 成長期: !isAnonymous()」라고 **전환 스위치로 설계해 둔 그대로**다.
ROADMAP §5 "인증은 verificationLevel 스위치 방식 — 초기 개방, 성장기에 조임"과 일치한다.
즉 **의도된 상태**이지 버그가 아니다. 다만 "언제 조일 것인가"가 미정이다.

**③ verificationLevel이 사실상 죽어 있다**
- 생성 시 `0` 고정, 클라이언트 승격 금지(규칙 강제) — 설계대로다.
- 그런데 **승격시킬 주체가 없다.** 승격은 Cloud Functions 몫인데 미구현(Blaze 플랜 필요).
- 1.0에서 외부 로그인(Microsoft 학교계정)을 **숨겼으므로**, 지금은 level 1이 되는 경로가 **아예 없다.**
- → **"학교 인증을 한 사람"이라는 개념이 현재 앱에 존재하지 않는다.** 준희 질문의 핵심은 여기다.

### 1-3. 지금 "학교"는 어떻게 정해지나
온보딩에서 **사용자가 목록에서 고른다**(`users.schoolDomain`). 메일 인증도 서류도 없다.
게스트도 고를 수 있다. 즉 현재의 학교 소속은 **자기 신고(self-declared)** 다.

### 1-4. 🔴 라운지 쪽지가 상대에게 안 간다
채팅 경로가 `schools/{schoolDomain}/chats`라서, 라운지(전국)에서 **타교 유저**에게 쪽지를 보내면
내 학교 경로에 방이 생기고 **상대는 영원히 못 본다**. QA-FEEDBACK 9-b 참조. 권한 개편과 같이 고쳐야 한다.

## 3. ✅ 권한 모델 — 준희안 채택 (2026-10-28)

### 3-1. 준희가 그린 그림
> - 우리 앱은 **처음에 로그인이 강제되지 않는다.** 대신 처음 받으면 **학교를 고른다**
> - **유학생의 숲 · 모두의 숲** = 로그인 안 해도 **누구나** 접근 가능
> - 그 아래 **공식 게시판** = 그 사람이 고른 **그 학교의 게시판**이 뜨고, **그 학교를 고른 사람만** 이용 가능

| 공간 | 접근 조건 |
|---|---|
| **みんなの森 / 留学生の森** | 🟢 **누구나** (로그인·학교 선택 불문) |
| **학교 공식 게시판** | **`users.schoolDomain`이 그 학교인 사람만** |

→ **이 모델을 채택한다.** 아래는 구현하면서 확인된 사실과, 남은 세부 결정이다.

### 3-2. ✅ 코드 확인 결과 — 이대로 구현된다 (3가지)

**① "로그인 안 해도 된다"는 이미 그렇게 돼 있다 — 단, 기술적으로는 익명 계정이 발급된다**
앱을 열면 Firebase **익명 인증**으로 uid가 자동 발급된다. 그래서 규칙의 `isSignedIn()`은 **항상 참**이고,
서버 입장에서 "로그인 안 한 사람"이라는 상태는 **존재하지 않는다.**
→ 🟢 **오히려 잘됐다.** 게이트를 「로그인 여부」가 아니라 **「`users.schoolDomain` 일치」** 로 걸면
준희안이 그대로 구현된다. 규칙 한 줄이면 된다:
```
allow read, create: if isSignedIn()
  && get(/databases/$(database)/documents/users/$(request.auth.uid)).data.schoolDomain == schoolDomain;
```

**② 학교는 온보딩에서만 고르고, 앱 안에 변경 UI가 없다** (`app/onboarding.tsx` → `updateSchoolSelection`, 호출처 1곳)
한 번 고르면 **앱 안에서는 못 바꾼다**(재설치해야 하고, 그러면 익명 uid가 새로 생겨 데이터가 날아간다).
→ 게이트가 생각보다 단단하다. 다만 **잘못 고른 사람·전학한 사람이 구제가 안 된다** → 3-3 Q2.

**③ 🔴 학부는 아직 안 고른다** — 준희 기억과 다른 부분
온보딩에서 고르는 건 **학교뿐**이다. `users.department`는 **프로필 학업정보를 쓸 때** 비로소 저장된다
(`userService.ts:165`). 강의검색·졸업요건은 화면에서 그때그때 고르는 구조다.
→ **학부 게시판을 제대로 하려면 학부 선택을 온보딩으로 올려야 한다.** S2(학교 분기)와 같이 하면 딱 맞는다.

### 3-3. 🔴 남은 세부 결정 4개

**Q1. 학교 게시판은 읽기도 막나, 쓰기만 막나?**
- **A) 읽기도 막는다** — 준희 표현("이용 가능")대로. 에타 방식. 「우리 학교 공간」 느낌이 확실해진다
- **B) 읽기는 열고 쓰기만 막는다** — 둘러볼 수 있어 유입에 유리
- 🟢 **권고: A.** **모두의 숲이 완전 개방**이라 둘러볼 곳이 이미 있다. 읽기를 막아도 잃는 게 적다

**Q2. 학교를 바꾸고 싶은 사람은?**
- 지금은 변경 UI가 없어 **재설치 = 데이터 전부 소실**이다. 구제 수단이 필요하다
- 🟢 **권고: 변경 UI를 만들되 「30일에 1회」 쿨다운 + 변경 이력 기록.**
  실수한 사람은 구제되고, 게시판을 갈아타며 돌아다니는 건 막힌다
- 담당: 온보딩·인증이라 **태희 축**

**Q3. 학부 게시판의 범위는?**
- **A) 읽기=같은 학교 전체 / 쓰기=같은 학부만** 🟢 **권고** — 글이 적을 때 읽기까지 막으면 학부 게시판이 죽는다
- **B) 읽기·쓰기 둘 다 같은 학부만**
- 🔴 **전제: 학부 선택을 온보딩으로 올려야 한다**(3-2-③). S2에 포함할 것

**Q4. 쪽지를 전국 스코프로 옮길 것인가?**
- 모두의 숲이 전국이면 **타교 쪽지가 반드시 돼야 한다.** 지금은 `schools/{학교}/chats`라 **상대가 못 받는다**(§1-4)
- 🟢 **권고: 최상위 `chats/`로 옮긴다. 그리고 지금이 옮기기 가장 좋은 시점이다** — 실유저 데이터가 아직 거의 없다.
  나중에 옮기면 기존 대화 마이그레이션이 필요해진다
- 담당: 규칙 변경이라 **태희 창구**

**Q5. 학교를 안 고른 「기타」 유저는?** → ✅ **이미 정해져 있다.** 학교 게시판 대신 숲으로
(AGENTS.md 준희 복귀 인계 §1). 이제 숲이 2개라 둘 다 쓸 수 있다. **준희안과 일치.**

### 3-4. 🔑 솔직하게 — 이건 담장이지 자물쇠가 아니다
학교를 **자기가 고르는** 것이므로, 마음먹으면 재설치해서 다른 학교를 고를 수 있다.
**진짜 자물쇠는 학교 메일 인증뿐**이고, 그건 Cloud Functions(Blaze 전환)가 필요해서 1.2 이후다.

**그래도 지금 단계에선 담장이 맞다:**
- 실수로 남의 학교 글을 보는 일이 없어지고, 「우리 학교 공간」이라는 느낌이 생긴다
- **재설치라는 마찰**이 있어서 실제로 넘어오는 사람은 거의 없다
- 🟢 **나중에 메일 인증을 붙일 때 같은 자리에 자물쇠만 바꿔 끼우면 된다** — 재설계가 안 생긴다
  (규칙의 `schoolDomain == schoolDomain` 조건에 `&& verificationLevel >= 1`만 더하면 끝)

### 3-5. ⚠️ 기술 비용 하나
규칙에서 `get(/users/$(uid))`를 호출하면 **읽기 1회로 과금**된다(쿼리당 1회, 같은 요청 안에서는 캐시).
Spark(무료) 일 5만 읽기 한도 안이라 **초기엔 문제없다.** 유저가 늘면 custom claims(Blaze)로 옮긴다.
→ `usersPublic/{uid}`에도 `schoolDomain`이 미러돼 있으므로 **어느 쪽을 읽어도 된다**(비용 동일).

## 4. ✅ 라운지 → **숲 2개로 분할** (2026-10-28 준희 결정)

### 결정 내용
> 「大学の森」가 앱 이름이니 **공간 이름도 숲으로 통일**한다.
> 지금의 **유학생 라운지 → 「みんなの森」(모두의 숲)** 으로 바꾸고,
> **「留学生の森」(유학생의 숲)을 하나 더** 만든다. — 준희

### 이게 좋은 이유
- 이름 체계가 **구조를 그대로 설명**한다. 학교 게시판(각자의 나무) → 모두의 숲 → 유학생의 숲.
- 「留学生ラウンジ」가 일본인 학생을 밀어내던 문제가 **공간을 나눠서** 풀린다.
  일본인은 모두의 숲으로, 유학생 전용 정보는 유학생의 숲으로 — **둘 다 잃지 않는다.**
- ROADMAP §5의 확산 전략("한국인 유학생 → 전체 유학생, 일본인은 다리")과 정확히 맞는다.

### 공간 3층 (확정안)
| 공간 | 일본어 | 범위 | Firestore |
|---|---|---|---|
| 학교 게시판 | (학교명) | 학교별 | `schools/{sd}/boards/...` (현행) |
| **모두의 숲** | **みんなの森** | 전국·전원 | `lounges/...` (현행 경로 재사용) |
| **유학생의 숲** | **留学生の森** | 전국·유학생 | 🔴 신규 — §4-3 참조 |

### 4-1. 카테고리 재배치 (제안)
현재 라운지 5개는 **전부 유학생 민원 성격**이라 그대로 두면 모두의 숲이 텅 빈다.
`loungeId`는 **절대 바꾸지 않고**(기존 글 보존) 소속 숲만 재지정한다.

| 기존 loungeId | 현재 라벨 | 이동할 곳 |
|---|---|---|
| `visa` | ビザ・在留 | **留学生の森** |
| `parttime` | アルバイト | **留学生の森** |
| `housing` | 住まい・不動産 | **留学生の森** |
| `market` | 売買・譲渡 | **みんなの森** (유학생 한정 정보가 아님) |
| `job` | 就活・キャリア | **みんなの森** (일본인 학생도 같은 고민) |
| 🆕 `chat` | 雑談・話題 | **みんなの森** — 🟢 **콘텐츠 시딩의 주 무대가 여기다** |
| 🆕 `nihongo` | 日本語・生活 | **留学生の森** (검토) |

> 모두의 숲이 3개(`market`·`job`·`chat`), 유학생의 숲이 3~4개가 된다. 균형이 맞는다.

### 4-2. 🔴 남은 설계 질문 (준희와 논의 계속 — §3과 같이)
1. **유학생의 숲에 누가 들어가나?**
   - 지금 유저 프로필에 **「유학생인가」 플래그가 없다.** `users`에 필드를 추가해야 한다(= 태희 창구).
   - 선택지: (a) 누구나 열람 가능, 쓰기만 유학생 (b) 자기 신고 플래그로 완전 분리 (c) 당분간 전원 개방
   - 👉 초기엔 **(c) 전원 개방 + 이름으로만 성격 구분**이 콜드스타트에 안전하다. 사람이 모이면 조인다.
2. **들어가는 입구를 어떻게 두나?** 지금은 게시판 탭 상단 **배너 1개**다. 숲이 2개가 되면 배너로는 부족하다.
   → **탭 상단 세그먼트**(학교 ↔ 모두의 숲 ↔ 유학생의 숲)가 자연스럽다. 에타가 이 구조다(첨부 스샷).
3. **학교 게시판의 이름도 숲으로 맞출 것인가?** (예: 明治の森) — 통일감은 좋지만 "우리 학교"라는 직관은 약해진다.

### 4-3. 구현 메모 (세션 S4)

  → `firestore.rules` 변경 없이 화면 분류만 바뀐다. 🟢 **규칙 배포 없이 OTA로 나갈 수 있다.**

## 7. 게시판 라인업 확장 (2026-10-28 준희 제안)

### 7-0. 먼저 좋은 소식 — 게시판 추가는 거의 공짜다
`firestore.rules`가 `match /boards/{boardId}/posts/{postId}`로 **boardId를 와일드카드**로 받는다.
즉 **새 게시판을 늘려도 규칙 변경·배포가 필요 없다.** `src/types/board.ts`의 `OFFICIAL_BOARDS` 배열에
한 줄 더하면 끝이고 **OTA로 나간다.** (파일이 `src/types/`에 있지만 **타입 변경이 아니라 데이터 추가**다 —
태희에게 공유만 하면 된다)

### 7-1. 🟢 설문조사 게시판 — 바로 하자
- **일본어명 제안**: 「アンケート協力」 / boardId `survey`
- **왜 좋은가**: 졸논·제미 논문 시즌(11~1월)에 수요가 확실하고, 리스크가 전혀 없다.
  그리고 **답해주면 나도 받는다**는 상호성이 생겨서 **자발적 재방문**을 만든다 — 커뮤니티 입장에선 이게 크다
- **글 양식 제안** (입력 템플릿을 미리 깔아주면 질이 올라간다)
  ```
  ・調査テーマ：
  ・対象：（例：明治大生 / 留学生 / 20代全般）
  ・所要時間：約〇分
  ・締切：〇月〇日
  ・リンク：
  ```
- ⚠️ **스팸 대책**: 외부 링크가 본문에 들어가는 유일한 게시판이 된다.
  초기엔 신고 기능으로 대응하고, 문제가 생기면 도메인 화이트리스트(Google Forms·Microsoft Forms 등)를 검토
- 🟢 **익명 해제(§8)와 궁합이 좋다** — 누가 부탁하는지 보이면 응답률이 오른다

### 7-2. 🟢 제미 게시판 — 차별화 포인트가 될 수 있다
- **일본어명 제안**: 「ゼミ」 / boardId `zemi`
- **왜 좋은가**: 제미 선발은 일본 대학 특유의 큰 이벤트(보통 2학년 가을~겨울)인데 **정보가 극단적으로 부족하다.**
  타 앱에도 제대로 된 게 없다. 그리고 **준희가 국제마케팅 제미 소속**이라 초기 콘텐츠를 직접 채울 수 있다
- 🔴 **「인기 순위」는 설계를 바꾸는 게 좋다** — 주관 투표로 순위를 매기면 **교원 평가**가 되고,
  낮게 평가된 교원 쪽에서 명예훼손 문제가 될 수 있다. 강의평과 달리 제미는 **교원 1명과 직결**이라 리스크가 더 크다
- 🟢 **대신 이렇게**: 두 가지로 나눈다
  | 구분 | 내용 | 성격 |
  |---|---|---|
  | **ゼミ紹介** | 모집인원 · 활동내용 · 선발방법(면접/과제/成績) · 합숙 유무 · 활동 빈도 | **사실 정보** — 안전 |
  | **選考体験記** | "나는 이렇게 준비했다" 본인 경험 | **본인 체험** — 안전 |
  | ~~인기 순위~~ | → **지원자 수·관심 등록 수로 자동 산출** | 객관 지표 — 안전 |
  - 학생이 진짜 알고 싶은 건 **"좋은 제미인가"가 아니라 "들어가기 어려운가"** 다. 객관 지표가 오히려 더 쓸모 있다
- **확장 가능성**: 데이터 구조가 `courses`와 비슷하다 → 나중에 **제미 검색**으로 키울 수 있다(1.2 이후)

#### 7-2-a. ✅ 2026-10-28 결정: **게시판만 만들고 유저가 올린다** (준희)
공식 데이터를 운영이 수집·게시하는 방식은 **하지 않는다.** 게시판만 열어두고
**제미 관계자·수강생이 홍보물·선고 결과·후기를 직접 올리는 방향**으로 간다.

**이 결정의 좋은 점**
- 🟢 **학내 자료 공개 여부 문제가 통째로 사라진다** — 올리는 사람이 당사자이고, 우리는 플랫폼이다
- 🟢 **교원 평가 리스크도 사라진다** — 운영이 순위를 만들지 않으니 명예훼손 구성이 안 된다
- 🟢 **운영 부담이 0이다** — 연례 데이터 갱신·검증이 필요 없다
- 👎 대신 **콜드스타트가 느리다** — 제미 관계자가 유입될 때까지 비어 있다

**그래서 마중물은 이렇게**
| 방법 | 내용 | 비고 |
|---|---|---|
| ① 준희가 직접 | 국제마케팅 제미 소개·선고 경험을 본인이 씀 | 🟢 **1건이라도 있으면 "이렇게 쓰면 되는구나"가 생긴다** |
| ② 제미 공개 인스타 소개 | 제미가 운영하는 **공개 계정**을 찾아 소개·링크 | 공개 계정이라 문제없다. MARKETING §7과 겸함 |
| ③ 글 양식 제공 | 「ゼミ名 / 担当 / 募集人数 / 選考方法 / 活動内容 / 雰囲気」 | 빈칸 채우기로 만들면 기여 장벽이 내려간다 |

> 📌 **공식 「応募状況」 데이터 활용은 보류**(드랍이 아니라 보류). 유저 기여가 쌓인 뒤
> "숫자도 있으면 좋겠다"는 요구가 나오면 그때 공개 여부를 확인해서 꺼내면 된다.
> 지금 결정으로 **§3 게시판 권한 결정을 기다릴 필요도 없어졌다** — 제미 게시판은 바로 열 수 있다.

### 7-3. 🟢 신오쿠보 맛집 — 留学生の森에 딱 맞는다

### 7-4. 🔴 출석코드 게시판 — 이것만 짚고 간다

**수요가 크다는 건 맞다.** 다만 다른 셋과 리스크의 성격이 완전히 다르다.

출석코드 공유는 대리출석(代返)이고, 일본 대학에서 **부정행위(不正行為)로 징계 대상**이다.
그런데 진짜 문제는 징계가 아니다. 순서대로 쓰면:

1. 🔴 **대학과의 관계가 끊긴다 — 이게 제일 크다.**
   `大学の森`는 **대학 커뮤니티 앱**이다. 메이지가 "이 앱 쓰지 마세요"라고 한 번 말하면
   신입생 유입이 막히고, 학내 홍보·공식 제휴 가능성도 같이 사라진다. 앱의 성장 경로 자체가 닫힌다.
2. **우리가 스스로 정한 규칙과 충돌한다** — [MODERATION.md](MODERATION.md)·CONTENT-OPS §7에
   이미 「시험 문제·레포트 공유(부정행위 방조)」를 금지로 두고 있다. 같은 계열인데 한쪽만 전용 게시판을 만들면
   신고 처리 기준이 무너진다.
3. **스토어** — 불법은 아니라 즉시 리젝 사유라고 단정할 순 없지만, 신고가 누적되면 리스크가 된다.

> 🔑 **핵심 구분**: 유저가 자유게시판에 자발적으로 올리는 것과, **앱이 전용 게시판을 만들어 주는 것**은
> 완전히 다르다. 후자는 앱이 **구조적으로 조장**하는 것이고, 대학이 보면 변명의 여지가 없다.
> 이름을 돌려서 지어도(「出席情報」 등) 대학 쪽에서 보면 같다 — 그런 완충은 의미가 없다.

#### 🟢 수요의 본질은 같고 리스크가 0인 대안
학생이 출석코드를 찾는 상황을 뜯어보면, 실제 수요는 대부분 이 둘이다.

| 대안 게시판 | 내용 | 평 |
|---|---|---|
| **「休講・教室変更」** (휴강·교실변경) | "오늘 2限 휴강", "교실 바뀜" | 🟢 **수요가 비슷하게 크고 대학도 환영한다.** 실시간성이 있어서 앱을 열 이유가 생긴다 |
| **「今日の授業」** (오늘 수업) | 못 간 수업에서 뭘 했는지 · 공지 공유 | 🟢 필기 공유로 자연스럽게 이어진다 |

**둘 다 "앱을 매일 여는 이유"를 만든다**는 점에서 출석코드보다 오히려 유지력이 높다.

#### ✅ 2026-10-28 결정: 「今日の授業」으로 간다 (준희)
출석코드 게시판은 만들지 않는다. 대신 **「今日の授業」**(오늘 수업) 게시판을 연다. boardId `today`.

## 8. 익명 체크박스 (2026-10-28 준희 제안) — 🟢 좋은 기능, 구현도 가볍다

> "에타 보니까 익명을 체크박스로 고를 수 있게 해뒀던데 이것도 좋은 것 같아.
> 디폴트 값은 익명 선택이고, 해제하고 싶으면 해제할 수 있게" — 준희

### ✅ 약관은 이미 열려 있다 (확인 완료)
`app/terms.tsx` **第6条1항**:
> 本サービスの掲示板等では、利用者間において**ニックネームまたは匿名**で表示されます。

**「닉네임 또는 익명」이라고 이미 써 있다.** 약관 수정 없이 바로 할 수 있다.
ROADMAP §5의 「익명성 유지」와도 충돌하지 않는다 — 그 항목은 **「운영자는 투고자를 특정할 수 있다」**는 뜻이고,
표시 방식을 고정한다는 뜻이 아니다.

### 설계
- `Post`/`Comment`/`LoungePost`에 **`anonymous?: boolean`** 추가. **기본값 `true`**(준희 안 그대로)
- 🔴 **`authorUid`는 무조건 그대로 저장한다** — 익명 해제는 **표시만** 바뀌는 것이다.
  AGENTS.md의 불변 제약(「투고의 authorUid는 법적 대응용 — 익명화·제거 금지」)은 그대로 지켜진다
- 🔑 **닉네임은 글에 스냅샷으로 저장한다** (`authorNickname`)
  - 매번 `usersPublic`에서 읽으면 **글 20개 = 읽기 20회**라 비용·속도가 나빠진다
  - 스냅샷이면 읽기 0회이고, **나중에 닉네임을 바꿔도 과거 글은 그때 이름 그대로** 남는다(이게 맞는 동작이다)
- **작성 시점에 고정.** 올린 뒤에 익명↔실명을 바꾸는 기능은 만들지 않는다 — 글을 본 사람과 안 본 사람 사이에 모순이 생긴다

### 왜 이게 §7과 맞물리나
**새 게시판 3개는 실명이 오히려 유용하다.**
- **アンケート協力** — 누가 부탁하는지 보이면 답해준다
- **ゼミ** — 제미 소개를 쓴 사람이 실제 소속이면 신뢰가 생긴다
- **新大久保グルメ** — 맛집 추천은 "이 사람 추천은 믿을 만하다"가 쌓인다

반대로 自由·質問·留学生の森은 익명이 맞다. **그래서 체크박스가 정답이다** — 게시판마다 강제하는 대신
사용자가 고르게 하면, 자연스럽게 각 게시판에 맞는 문화가 생긴다.

### 🔴 주의 1건
- 실명(닉네임)으로 올린 글에 **차단·신고**가 걸렸을 때의 동작은 기존과 같다(`authorUid` 기준이라 영향 없음).
- 다만 **실명 글은 신상 특정 위험이 올라간다.** 체크 해제 시 **"닉네임이 공개됩니다" 1줄 안내**를 띄울 것
- 타입 변경이므로 **태희 창구**
